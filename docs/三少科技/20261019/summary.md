## 內容總結

本集解讀 GitHub 專案 **Pstack**——由 React 核心團隊成員 **Lauren Tan（網名 Poto）** 公開的一套「AI 代理工作規範」。他目前在 **xAI** 服務，此前曾在 **Meta、Netflix、Coinbase** 處理數百萬行程式碼，並參與 **React Compiler** 的開發維護。

Pstack 的立論不落在「AI 能不能寫出好程式碼」，而是落在**「我不看每一行程式碼，我憑什麼信得過 AI 交上來的東西」**。整個體系由 **24 項原則、23 個工作流程、32 項技能**（合計近 80 件物品）組成，針對「不信任」拆解成五種類型，每一類都給出具體可複製的做法。

**最終結論**：AI 工具越強、同時開得越多，你反而越累——因為每個 agent 交來的東西都要逐行檢查，等於一次招了五個實習生，自己成了最忙的人。**想走快，先走深**：先把規則立好、檢查做扎實，才敢同時並行開一堆 AI（作者稱之為「無憂並行執行」）。核心金句是「**大多數時候最慢的一步是檢查**——因為檢查通常在等人；AI 自己無法檢查自己，你開再多也只是多了一堆沒人檢查的活排隊等你」。

### 五種「不信任」與對策

| # | 類型 | 具體對策 |
|---|------|----------|
| **1** | 怕方向跑偏 | **不做計劃**：「我不相信計劃，最好的需求文件就是程式碼本身」；改為**先做原型**（粗劣樣品、用完就拋，23 個流程中唯一不講究的一個）；**Architect**：動手前至少想出兩個完全不同的方案；**Arena**：多個 AI 各做一份（像招標），用**不同模型**評分，挑一份當基準再移植其他版本好點子 |
| **2** | 怕寫太多 | **懶人協議（Laziness Protocol）**：能刪就刪、改動越小越好——「寫更少的程式碼行勝過編寫一大堆看起來優雅的樣板」；bug 修復要求**每一行上線代碼都要有證據**（實際跑起來看問題出在哪）；「以防萬一」的程式碼只是猜測，**不算修好，不准上線**；證據顯示猜錯時，連同該猜測的程式碼一起刪 |
| **3** | 怕假裝完成 | **Prove It Works（實證檢驗）**：第一句就把「完成」定義成可判對錯的條件；要求「原始輸出一個字都不能變、新格式要能被其他程式讀出來、兩種都用真實專案跑一遍，把結果給我看」→ AI 手上就有**三個可執行的檢查**；「請優化一下、做得好一點」= 讓它**猜你的心情**；好的回答會直說「我無法確定」，**缺乏證據卻特別自信的回答本身就是警報** |
| **4** | 怕自賣自夸 | **Attack Assumptions（攻擊前提）**：你一直覺得網速太慢，換了兩種提速辦法都沒用，還在找第三種 → 該懷疑的是**「網速慢」這個前提本身**；每一次失敗都是一條證據，證明前提可能錯了 |
| **5** | 怕查不到 | 每個任務先**複製流程步驟到待辦清單**；被跳過的步驟不會悄然消失，會留在清單裡寫明原因（**連偷懶都得留下痕跡**）；每條原則必須說清楚它改變了哪個決定，否則要「展示你的工作成果」；**記憶行**：做了什麼、為什麼、證據是什麼、結果如何（有點像飛機黑盒子） |

### 交付與檢查的硬規則
- **完成標準提前寫死**：開工前先把「完成」定義成能判對錯的條件（例：所有測試都通過、新舊兩張截圖一個項目都不差、所有改動全部合進去）
- **卡住不等於完成**：改變方法繼續做；真的走進死胡同要坦承——**絕不能偷偷降低標準宣布勝利**。反之，「幹了四個小時」若沒有結果，等同於什麼都沒做
- **Leverage（槓桿）**：能寫成腳本自動化的，不要手動一步步做——「一個每次結果都一樣的小程式，能把『相信我』變成『你自己跑一下』」
- **檢查者必須換人**：為改動打分的 AI **絕不能**是寫那個改動的 AI（等於讓學生自己改自己的考卷）；所有待合併的改動都要用**一個全新的 AI** 實跑一遍
- **「綠燈 ≠ 安全」**：全綠只代表所有自動檢查通過，工作流程僅標記為「準備合併」；**真正的合併是另一個獨立決定**
- **Interrogate 不靠換人設**：常見的「你現在扮演嚴格審查員」在 Pstack 不用——「換同一個模型的角色，它還是看不到同樣的盲點」；正確做法是**同時給幾個不同模型機會各自挑刺**。預設分工：**Claude Code 負責最難的程式碼改動，Opus 5.5 負責文字與判斷**；但若檢查 AI 唯一的工作只是把一條命令再跑一遍，**那是走過場，不是檢查**

### 程式碼可讀性
- **降低讀者負擔（30 秒測試）**：找一個第一次看這段程式碼的人，看他能否在 **30 秒內回答兩個問題**——「這個數值是從哪裡來的？」「什麼改變了這一切？」答不上來就代表太肉，必須刪掉中間不必要的複雜度
- **CommentsEqual 檢查器**（字幕稿用字）：整個設計建立在「痛恨程式碼中的註解」上，出場第一句是「**是的，哈哈，是的**」。邏輯是：如果程式碼需要靠註解才看得懂，代表**程式碼本身沒寫清楚**——它不讓你補註解，而是讓你回去**改程式碼**；命名要簡單明瞭，太長的名稱要拆開，讓程式碼自己說話
  - 實例：開發者 B 稱當天省了約 2 小時——他讓 AI 改一個介面，AI 沒有為了讓改動「看起來令人印象深刻」而堆一堆包裝，否則整個下午都得跟在後面收拾爛攤子
  - 註：原文即聲明這只是個人敘述，**非嚴謹對照實驗**

### 歷史追蹤與復盤
- 追查「當初為什麼這樣設計」時，把**確鑿證據與自己的推論分開寫**；查不到原因時要老實說「因為當初沒人寫下為什麼」——**這本身就是答案**
- 「過程查得到，錯才改得掉」；同一個錯出現第二次，**不要只在說明書加一句提醒**——能改成會報錯的自動檢查就改（原則原話：「提醒本身就是一種症狀」）
- **Reflect**：任務完成後可讓三個 AI 一起事後分析，把學到的東西寫回對應的技能集

### 信任邊界與大型編排
- **能撤銷的，直接做**：寫程式碼這類可撤銷的事，做完在群組說一聲、更新任務清單、跑一次測試，**不必問人**
- **不可撤銷的，必須停下來問人**：強制覆蓋共用程式碼、部署到正式環境、刪除資料、對客戶發訊息
- **Orchestrate（編排）**：針對要跑好幾天的大專案——一個 AI 當**指揮官**，只負責明確任務與做判斷，**自己一行程式碼都不寫**；底下可帶**幾十到幾百個工作型 AI**。示範：「這次遷移，你要一直觀察到所有內容合併完成；我一天來看兩次」
- **從結構上防止衝突**：「你無法管理多人同時編輯同一份內容」——要嘛**不讓他們共用**，要嘛**排定先後順序**或**指定一個人說了算**

### 適用邊界與起步
- **不是所有事都要用**：整套都在燒 token（用量與錢）；細微、明顯的改動**不需要專業模式**
- **第一天不需要一堆技能，甚至不需要整個 tech stack**：先正常使用，看 AI 在哪裡出問題；**同一個問題出現第二次再**加一個技能或檢查
- 想試可同時安裝 **Claude Code** 與 **Cursor**；記住三個指令即可：`/setup stack`（選預算和模型）、`/auto mode`（加在任何想認真做的任務前）、`/pstack help`（不知道用哪個時問它）

## 🧭 收尾提問（行動框架）

下次想多開幾個 AI 之前，先問自己一句：**「我現在不敢放手的那件事，到底在怕什麼？」**

| 怕什麼 | 補哪一個 |
|--------|----------|
| 怕方向跑偏 | Architect / Arena + 先做原型 |
| 怕它寫太多 | 懶人協議 |
| 怕它假裝完成 | Prove It Works + 完成條件前置 |
| 怕它自賣自夸 | Attack Assumptions |
| 怕做了你查不到 | 記憶行 + 待辦清單留痕 |
